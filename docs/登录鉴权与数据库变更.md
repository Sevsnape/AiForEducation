# 登录鉴权与数据库变更

> 结论：**需要。** 前端登录对应后端用户体系；原有 `users` / `role_bindings` 不够，必须补密码与会话表，并改后端鉴权服务。

## 1. 为什么要改库

| 已有 | 缺口 |
|------|------|
| `users` 身份主体 | 无 `password_hash`，无法本地账密登录 |
| `role_bindings` 三角色 | 登录后需选定/解析角色写入会话 |
| `audit_logs` | 可记登录失败/登出，但缺会话实体 |
| — | 无 `auth_sessions`，无法做 token 校验与登出吊销 |

## 2. 表/字段变更

### `users` 增补

| 字段 | 说明 |
|------|------|
| `email` | **唯一**，登录主标识 |
| `password_hash` | PBKDF2 等哈希；SSO-only 可空 |
| `last_login_at` | 最近成功登录 |

### 新表 `auth_sessions`

存 **token 哈希**、选用角色、过期与吊销时间。客户端持有明文 token，服务端只存 hash。

## 3. 后端改造要点

1. **AuthService**：注册/创建用户（管理员）、登录、登出、`resolve_token`  
2. **密码**：只存 hash，永不回传明文  
3. **Agent 调用**：`invoke` 应携带会话 token（或网关已鉴权的 user_id+role），禁止前端自己申报角色越权  
4. **用户管理 API**（管理端）：列表/启停/绑定角色 —— 与 `role_bindings` 对齐  
5. **运行时存储**：当前可用内存仓储演示；生产切 PostgreSQL ORM
