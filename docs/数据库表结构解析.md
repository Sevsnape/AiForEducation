# AIFOREC 数据库表结构解析

> 对应脚本：[sql/001_init.sql](./sql/001_init.sql)  
> 表级/列级注释已写入 SQL 的 `COMMENT ON`（可在 PostgreSQL 中用 `\d+ 表名` 查看）  
> 精简索引版：[数据库表结构.md](./数据库表结构.md)

本文用白话说明：**这套 SQL 在干什么、每张表干什么、字段各自什么意思、和产品设计怎么对应**。

---

## 0. 先看整体：这套库在解决什么

系统要同时做到三件事：

1. **学生能聊天、练习、被记住**（会话 + 画像）  
2. **老师能出题、在授权下看学情**（产物 + 班级关系 + 同意）  
3. **心理/支持信息老师看不到，但系统要能审计**（support 隔离 + audit）

所以表不是「一个聊天记录表打天下」，而是按职责拆开：

```text
身份租户          会话历史           长期记忆            学业产物           合规
users             threads            student_profiles    artifacts          audit_logs
organizations     messages           profile_corrections learning_events    consents
class_groups      session_summaries                      weekly_summaries
role_bindings
memberships
```

**和 LangGraph 的分工**

| 存在哪 | 存什么 |
|--------|--------|
| 本 SQL 库 | 用户、同意、消息原文、画像、题包、审计 |
| LangGraph Checkpointer | 同一次会话里图怎么跑到一半（续聊/中断），不是业务主档 |

## 1. 身份与租户

### 1.1 `users` — 人

所有账号的基础表。不管是学生还是老师，先有一个 `users` 行。

| 字段 | 含义 |
|------|------|
| `id` | 主键 UUID |
| `external_id` | 对接学校 SSO / 微信登录等外部 ID，可空 |
| `display_name` | 显示名 |
| `email` | 邮箱，可空 |
| `status` | `active` 正常 / `disabled` 停用 / `deleted` 逻辑删除 |
| `created_at` / `updated_at` | 创建、更新时间 |

**注意**：角色不写死在 `users` 上，因为同一个人可能既是某校老师，又是个人版学生。

---

### 1.2 `organizations` — 学校/机构

混合场景里的「租户」。个人版可以没有组织。

| 字段 | 含义 |
|------|------|
| `id` | 组织主键 |
| `name` | 名称 |
| `status` | `active` / `disabled` |
| 时间戳 | 创建、更新 |

---

### 1.3 `class_groups` — 班级

教学班。老师「能不能看这个学生的学情」，要靠班级成员关系判断。

| 字段 | 含义 |
|------|------|
| `org_id` | 所属学校；学校删了班级 `org_id` 置空（`ON DELETE SET NULL`） |
| `name` | 班级名 |
| `grade` | 年级，如初二 |
| `subject` | 主学科（可选） |
| `status` | `active` / `archived` |

---

### 1.4 `role_bindings` — 角色绑定

回答：「这个用户在哪个范围是什么角色？」

| 字段 | 含义 |
|------|------|
| `user_id` | 谁 |
| `role` | `student` / `teacher` / `admin` |
| `org_id` | 作用在哪个组织；空=个人/全局 |
| `class_id` | 作用在哪个班；可空 |

同一用户可以有多条绑定（例如 A 校老师 + 个人学生）。

---

### 1.5 `memberships` — 班级成员

比 `role_bindings` 更「教务」：谁在哪个班当学生/老师。

| 字段 | 含义 |
|------|------|
| `class_id` / `user_id` | 班与人 |
| `member_role` | 在班身份：`student` 或 `teacher` |
| `status` | `active` 在班 / `left` 已离班 |

**产品含义**：老师离班或学生转班后，`left` 应导致老师失去该生学情读取权。

---

### 1.6 `consents` — 同意开关

控制个性化、历史留存、是否把**学情**分享给老师。  
**MVP：由管理员在后台配置**（校级默认 + 学生覆盖），学生端暂不开放自助修改。见 [同意策略管理员配置.md](./同意策略管理员配置.md)。

权责体系的核心开关，不是装饰字段。

| 字段 | 默认倾向 | 含义 |
|------|----------|------|
| `learning_personalize` | true | 能否用画像做个性化 |
| `history_retain` | true | 能否留存聊天历史 |
| `share_learning_with_teacher` | **false** | 学习侧学情是否给老师 |

`org_id` 可空：空表示个人默认策略；有值表示在某学校下的策略。

**硬规则**：即使学情共享打开，**支持侧（心理）数据仍不对老师开放**。Consent 管的是 learning，不是 support。

---

## 2. 会话与历史（学生私有为主）

### 2.1 `threads` — 会话线程

历史页上的「一条对话」。

| 字段 | 含义 |
|------|------|
| `owner_user_id` | 会话主人（学生） |
| `title` | 标题 |
| `primary_intent` | 主意图：练习/问问题/心情/混合/闲聊/安全 |
| `client_mode` | 前端点的模式（出题/练习/聊聊心情），空=自动识别 |
| `started_at` / `last_active_at` | 开始与最近活跃 |
| `deleted_at` | 软删除；非空=学生删了 |

`id` 常与 LangGraph 的 `thread_id` 对齐，方便续聊。

索引 `idx_threads_owner_active`：快速列出「我的未删除会话」。

---

### 2.2 `messages` — 消息原文

每一句用户/助手内容都在这里，**包括心情对话原文**。

| 字段 | 含义 |
|------|------|
| `thread_id` | 属于哪次会话 |
| `turn_id` | 同一回合的捆绑（问+答） |
| `role` | `user` / `assistant` / `system` / `tool` |
| `content` | 正文 |
| `intent` / `agent_name` | 本回合意图与处理专家 |
| `risk_level` | `none` / `watch` / `high` |
| `trace_id` | 追踪 ID |
| `metadata_json` | 小扩展信息（勿塞整份大题包） |

**可见性**：仅 owner；老师侧接口不应查此表的 counsel 内容。

---

### 2.3 `session_summaries` — 会话摘要

一次会话结束后（或定期）生成的短摘要，给画像合并用，避免每次把全文塞进模型。

| 字段 | 含义 |
|------|------|
| `summary_text` | 短摘要正文 |
| `learning_tags` | 学习标签数组 |
| `support_tags` | 支持标签数组（不对老师） |
| `model_name` | 用了哪个模型；规则占位时可空 |

---

## 3. 学生长期画像

### 3.1 `student_profiles` — 「AI 记得你」的数据底表

一人一行。Agent 每次对话注入的是它的**切片**，不是整库原文。

| 字段 | 含义 |
|------|------|
| `student_id` | 等于 `users.id` |
| `profile_version` | 版本，合并/纠正时 +1 |
| `learning_json` | 学习侧 JSON（薄弱点、难度甜区、目标等） |
| `support_json` | 支持侧 JSON（情绪主题、风险、`safe_summary` 等） |
| `source` | `auto_summary` / `student_correction` / `hybrid` |
| `needs_resummary` | 删历史后等场景标记需要重算 |

**JSON 里放什么**：见《系统设计草案》第 5 章 Profile 字段。  
**老师**：最多看授权后的 learning 字段；**禁止 SELECT support_json**。

---

### 3.2 `profile_corrections` — 学生纠正记录

学生在「AI 记得你」里改画像时落库，方便追溯「是系统总结错了还是学生改过」。

| 字段 | 含义 |
|------|------|
| `domain` | `learning` 或 `support` |
| `patch_json` | 结构化补丁 |

---

## 4. 学业产物与事件

### 4.1 `artifacts` — 题包 / 练习包等

对话是过程，产物是结果。老师审题看产物，不必翻聊天。

| 字段 | 含义 |
|------|------|
| `owner_user_id` | 创建者 |
| `thread_id` | 从哪次会话来；会话删了可置空保留产物 |
| `artifact_type` | `question_set` / `practice_set` / `explanation` / `export` |
| `content_json` | 题目列表等结构化内容 |
| `status` | `draft` → `reviewed` → `published` / `archived` |
| `version` | 修订版本 |

---

### 4.2 `learning_events` — 学习事件流

「做了什么题、对不对」的流水账，用来算正确率、更新薄弱点。

| 字段 | 含义 |
|------|------|
| `event_type` | `answer` 答题 / `hint` 看提示 / `complete_set` 做完一套 / `retest` 再测 |
| `knowledge_tags` | 知识点 |
| `is_correct` | 是否答对（非答题可空） |
| `difficulty` | 1–5 |
| `payload_json` | 作答详情等 |

---

### 4.3 `question_asks` — 学业提问模块

学生「问了哪些知识点」的事件表，驱动管理端/教师端**模块热点**与**个人提问分布**。与 `learning_events`（答得怎样）互补。详见 [学情分析与问题模块.md](./学情分析与问题模块.md)。

| 字段 | 含义 |
|------|------|
| `module_tag` | 知识点/模块（如二次函数） |
| `intent` | 仅学习意图：`practice` / `question_gen` / `diagnose` / `general` |
| `question_preview` | 截断脱敏摘要，**不是**心情原文 |
| `org_id` / `class_id` | 聚合作用域 |

**硬规则**：`counsel` / `safety` 回合不得写入本表。

---

### 4.4 `learning_plans` — 学习计划共创

学生与 AI 对话生成的学业计划（目标、步骤、聚焦模块）。详见 [学习计划共创.md](./学习计划共创.md)。

| 字段 | 含义 |
|------|------|
| `horizon_days` | 计划跨度（天） |
| `status` | `draft` / `active` / `completed` / `archived` |
| `content_json` | goals / steps / focus_modules 等 |

---

### 4.5 `weekly_summaries` — 成长周报

历史页「成长总结」Tab 的数据。

| 字段 | 含义 |
|------|------|
| `week_start` | 周起始日 |
| `learning_text` | 本周学了什么 |
| `support_text` | 本周情绪/压力侧（**仅学生**） |
| `next_steps_json` | 下一步建议列表 |

一人一周唯一（`UNIQUE (student_id, week_start)`）。

---

## 5. 审计 `audit_logs`

用来回答：「谁在什么时候对什么做了什么，目的是什么？」

典型写入场景：

- 老师试图进 counsel → `guard_deny`  
- 高风险短路 → `safety_reply`  
- 数据导出、管理员查看  

| 字段 | 含义 |
|------|------|
| `actor_user_id` | 操作者；用户删了可置空，日志仍留 |
| `action` | 动作名 |
| `resource_type` / `resource_id` | 作用对象 |
| `purpose` | 如 `teaching` / `safety` / `compliance` |
| `detail_json` | 细节；**应脱敏，不要塞心理原文** |

---

## 6. 外键与删除策略（为什么这样写）

| 关系 | 策略 | 原因 |
|------|------|------|
| 用户删 → 其会话/画像/事件 | `CASCADE` | 人没了，私有数据一起清 |
| 组织删 → 班级 `org_id` | `SET NULL` | 班可暂留，避免误伤 |
| 会话删 → 消息 | `CASCADE` | 消息从属于会话 |
| 会话删 → 产物 `thread_id` | `SET NULL` | 题包可能还要留着 |
| 用户删 → 审计 actor | `SET NULL` | 审计要留，人可以空 |

---

## 7. 按角色「谁能碰哪些表」（MVP）

| 表 | 学生 | 老师 | 管理员 |
|----|------|------|--------|
| `messages`（含 counsel） | 自己的 | ❌ | 合规极少数 |
| `support_json` / `support_text` / `support_tags` | 自己的 | ❌ | 合规极少数 |
| `learning_json` / `learning_events` | 自己的 | 授权班级 + consent | 审计 |
| `question_asks` | 自己的 | 授权班级聚合（无 preview 原文亦可） | ✅ 校级聚合 |
| `artifacts` | 自己的/已发布 | 自己创建 + 可见已发布 | 审计 |
| `audit_logs` | 通常不可见 | ❌ | ✅ |

## 8. 在数据库里查看注释

PostgreSQL：

```sql
-- 看表注释
SELECT obj_description('student_profiles'::regclass);

-- 看列注释
SELECT a.attname, col_description(a.attrelid, a.attnum)
FROM pg_attribute a
WHERE a.attrelid = 'student_profiles'::regclass
  AND a.attnum > 0 AND NOT a.attisdropped;
```

或在 `psql` 中：`\d+ student_profiles`
